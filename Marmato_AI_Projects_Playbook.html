How to use this file

  1. Assign a project owner and reviewer. Read shared setup, then the project’s own instructions.
  2. Create the two named Google Sheets workbooks and shared tabs. Download the project header templates and import them into the relevant tabs.
  3. Replace sample configuration values with Marmato-approved rules. Example services, target industries and weights are illustrative, not verified Marmato facts.
  4. Build the Make scenario using the common wrapper and project-specific processing steps. These are implementation recipes, not imported or tested Make blueprints.
  5. Run synthetic tests, then a representative 200–500-contact pilot. Review quality and cost before scaling.

This HTML works offline and contains no external scripts or API keys. It documents the workflows; it does not connect to your Google account or run automation. The website project describes how to assess marmatodigital.com; this document does not claim a completed website audit.

3. Common Make scenario wrapper — applies to all projects

  1. Create a scenario and connect Google Sheets. Select the source workbook by spreadsheet ID and the exact project tab. Use an account with access only to the needed files. Store AI credentials in a Make connection or secure HTTP credential store, never in Sheets or this HTML.
  2. Set the scenario schedule to manual for development, then a suitable interval. First module: Google Sheets → Search Rows, filter process_status=READY, limit 10 for the first test. A scheduled Search Rows pattern handles the existing contact backlog and retries; Watch New Rows is optional only for append-only future inputs.
  3. Load configuration: Google Sheets → Search Rows on Config, matching project_id and active=TRUE. Require exactly one active version. Parse config_json with JSON → Parse JSON. Missing or multiple active configs stop the job for review.
  4. Build an idempotency key: result_id = project_id + ':' + job_id + ':' + record_version + ':' + config_version + ':' + prompt_version. Search the destination by result_id. If a completed result exists, repair source status to DONE and skip the AI call. For reprocessing, increment record_version or the relevant version; never silently replace an approved result.
  5. Claim the row: Google Sheets → Update a Row. Set process_status=PROCESSING, increment attempt_count, save UTC updated_at. Use the row number from the current search result, not a stored row number. Run one scenario worker per project; Sheets does not provide atomic locking. Higher concurrency requires a transactional queue or lock store.
  6. Apply the project-specific steps below. Use Tools → Set multiple variables for simple normalization and arithmetic, Router plus filters for branches, Array aggregator for grouped evidence, and Iterator only for array items. Search Rows already emits row bundles; do not add an Iterator around those bundles.
  7. Call AI with the system and user templates. JSON → Create JSON must serialize prompts and record values; do not concatenate raw text into JSON. Configure the strict output schema shown in each project.
  8. Validate output: parse the response, parse each JSON-encoded _json field, check expected inner types, source IDs, categories, IDs, ranges and mandatory rules. Schema conformity alone does not establish factual accuracy. Refusals, incomplete output and invalid data go to review.
  9. Save: Google Sheets → Add a Row in the project destination for a new result_id. Populate metadata from Make, AI fields from parsed output and deterministic fields from rules. Default review_status=PENDING. For a failed-write retry, search by result_id before writing again.
  10. Finish: Update source status to DONE only after output is saved. DONE means processing complete, not business approval. Add Run_Log and Review_Queue rows. Reviewer chooses APPROVED, REJECTED or NEEDS_CHANGES; approved outputs become eligible inputs for downstream projects.

Operations, testing & employee handover

Error and retry design

  • Use READY → PROCESSING → DONE, with ERROR, REVIEW and BLOCKED for exceptions. Review approval is a separate field.
  • Enable Store incomplete executions in Make scenario settings. Attach error routes to HTTP, AI and Sheets writes. Log job_id and a redacted error message; never log credentials.
  • Retry transient rate-limit and connection errors with bounded backoff, for example 30/60/120 seconds with jitter, honoring Retry-After where available. Use Make retries/incomplete executions rather than an unbounded synchronous loop.
  • Do not retry bad credentials or invalid schemas repeatedly. Missing evidence, invalid categories, model refusal and conflicting input require review. After three failed attempts, set ERROR and create a review task.
  • Handle stale PROCESSING jobs through manual review or a recovery scenario after a configurable timeout, for example 30 minutes. Check for an existing result_id before resetting to READY.
  • When one part of a save fails, preserve the completed destination row. Repair queue/log state rather than calling the model again. Sequential execution and idempotency checks reduce duplicates; Sheets is not an exactly-once transactional system.

Scaling the 25,000-contact database

Begin with 20 synthetic tests, then 200–500 representative records. Batch 10–50 ready rows per scheduled run initially and adjust after measuring API limits and Make credit consumption. Cache account research by verified domain and snapshot date. Score each account once rather than once per contact. Avoid the roughly 312 million possible contact pairs from all-pairs duplicate comparison; use candidate blocking.

Measure actual pilot usage before forecasting. Estimated total cost = measured per-contact processing cost × eligible contacts + per-account research cost × unique accounts + fixed reporting cost. Include review time, enrichment/extraction subscriptions, Make credits and retries; not every project should run across all contacts.

Quality and data handling

  • Keep the original dataset unchanged and preserve source provenance. Treat unknown permission as a review condition, not permission to contact.
  • Use approved business data only; minimize personal fields sent to AI. The account/team chooses approved vendors and retention settings. The API request’s store=false flag does not replace vendor data-handling review.
  • Maintain one authoritative suppression list and check it again immediately before any future outreach send. These projects produce drafts; no email send, public publishing, CRM merge or deletion is included.
  • Require evidence IDs for factual research outputs; validate source membership and age. Model confidence alone must never trigger approval.
  • Use deterministic checks for numeric calculations, validation, scoring and URLs. Do not trust a model-generated formula, SQL statement or executable code from an input record.
